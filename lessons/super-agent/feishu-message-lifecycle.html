A三个入口、两条边界、一次反向读取

所有路径最终都汇到同一个 receive() helper；分叉只在 Intake 里发生一次。

三个入口（从第 5 步起同路）

  • 实时事件流 feishu-loops.ts:86-97 → receive():27
  • 历史补收 backfillChat():188 → receive():27
  • 话题轮询 pollThread():259 → receive():27
  • 都靠 feishuTriggerId() 的确定性 ID 在 intake.ts:23 去重
  • 旁路：runtime.ts:194 的 Runtime.receive 直接进 Passes，HTTP / 工具走这条

两条边界

  • 端口缝 core/ports.ts:12-134：SourceScope / Policy / Assessor / Executor / Outbox / Repositories 六个接口。Engine 不知道有飞书、SQLite 或 lark-cli
  • 事务缝 engine.ts:48 开始 → intake.ts:61 结束。所有跨聚合写入在一个 repo.atomic() 里
  • 同步 / 异步缝：intake.receive 返回前消息已完整落库但还没被理解；passes.ts:37 的 request() 才启动理解

同一条消息被读 3 次

  • 推：事件流 feishu-loops.ts:86-97
  • 拉：主 Session 评估时经 admissionContext → feishu-read.ts:153-171 反向读 message/root/parent/thread
  • 再拉：工人侧 sourceLink / repliesTo（dsh.ts:345-350、feishu.ts:69）
  • 三条完全不同的代码路径，读的是同一条飞书消息

C从这条链读出的设计决策

  • Source 永远拿不到 Engine。SourceContext 是能力白名单（host.ts:31-66），中间隔 source-context.ts 与 passes.ts 两层闭包——不是靠接口隐藏，是装配时就没把引用传下去。
  • 收得到 ≠ 想得动。Intake 同步落库，Passes 异步理解；pump() 合并并发，2 秒兜底时钟，暂停/setup 未完成时消息照收（passes.ts:58）。
  • 过滤也留痕。filtered 照样存进仓库（intake.ts:27），审计能回答「这条为什么没反应」。
  • 回信地址随消息出生。Trigger.channel（feishu-trigger.ts:8-9）一路带到 Replies.reply；出核时 channelAllowed 再查一次「这个群现在还收不收」（feishu.ts:62-63）。
  • 一切跨域副作用都持久化。assessment / launch / delivery / relay / notice / reply 六种 effect 在事务内 enqueue、提交后派发、失败指数退避、按 requestId 幂等（effects.ts:11-24,61-65,130-146）。
  • 确定性 ID 换来幂等：feishuTriggerId（:18）、ack id（replies.ts:56）、--idempotency-key（feishu-channel.ts:23）、AgentDelivery.send 的 requestId（delivery.ts:68-86）。
  • 跟随优先于评估。followupOwners()（model.ts:75-88）让已有工单的人话直接给工人，主 Session 只能 stop（evals.ts:148），避免两个决策者。
